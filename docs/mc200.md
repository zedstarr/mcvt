# MC200 / ROM v2.12F: investigation notes (parked)

MCVT 1.0 was built and tested on an MC400 with ROM v2.60F. This page records
what was found when trying it on the MC200 (ROM v2.12F, 640×200 screen), so
the work can be picked up again later.

**Status:** MCVT does not run on v2.12F. It starts, creates and draws its
window, then is ended silently by ROM code before the user can do anything.
The cause has not been found. Support is parked.

## Test set-up

- The joehaines.com browser emulator, `mc200` machine (ROM v2.12F, 128 KB RAM,
  no serial module). TERM.APP reports "device does not exist" for TTY:A and
  then opens normally.
- Diagnostic builds of MCVT that write a step-by-step log to `M:\MCVT.LOG`
  (each line written and the file closed at once, so the log survives the
  process dying).
- MAME (current source, and 0.289 on macOS) cannot be used: the `mc200` and
  `mc400` machines do not boot v2.12F (see below).

## What was established

| Step | Result on v2.12F |
| --- | --- |
| Start-up, settings, opening TTY:A | Works. TTY:A fails with -41 (no device); MCVT handles it. |
| Window of 1.0 is ~400 px tall, larger than the screen | Not the cause (the screen-fit build fails too). |
| App manager init (`am_init`), command manager, menu bar resource | Works. |
| Font search | **Bug found and fixed.** MCVT asked about fonts 0–7. Only the system font and the three ROM fonts (SMALL, BIG, MONO) exist on either ROM. On v2.60F asking about a missing font returns an error; on v2.12F it kills the process at once, with no dialog. The loop now stops after the fourth font, which gives the same choice (MONO, 7 px) on the MC400. |
| Screen size | The window server client holds the screen size at +0x78/+0x7A: 640×200 on the MC200. The screen-fit code sizes the terminal to 80×15. |
| Window creation and layout (frame and client) | Works; the frame is drawn. |
| First redraw | Works completely. Every drawing call was followed by a synchronous window-server request: clear, bold and normal text, the inverse cursor block all succeed. |
| After the first redraw | The process ends silently inside ROM code. No further MCVT method is called (keys, menu commands, Exit, focus, redraw, serial reader all log on entry and none appear), and the app manager's event loop does not return. |

Ruled out as the cause:

- **Memory**: 77 KB free before starting; a build with 4 KB less static data
  fails the same way.
- **The menu bar**: a build without one fails the same way.
- **The focus-window pointer** MCVT writes into the window-server client
  (+0x38): a build that does not write it fails the same way.
- **Class layouts**: all 55 OLIB and 77 WIMP classes have the same instance
  sizes and method counts in v2.12F and v2.60F, and the window-server client
  uses the same field offsets.

## Differences seen between the ROMs

- Same font files, same OLIB/WIMP class tables and method numbering.
- Much of WIMP.DYL in v2.12F was compiled with a **stack-based calling
  convention** (arguments at `[bp+4]`, `[bp+6]`…, sends through a local helper),
  where v2.60F passes them in registers (`bx`=self, `dx`, `si`, `di`) and
  sends with `int 0CFh`. OLIB converts between the two, and MCVT's methods are
  called correctly on both, but it shows the libraries were rebuilt between
  versions, not just patched.
- Methods that differ in code (not just addresses) include: class 18 (frame
  window) m9, m13, m14, m17, m27–m32, m41–m44; class 14 m34, m36–m40; class
  69 (app manager) m1, m5, m15, m16; class 66 (command manager) m5; class 68
  (ws client) m26; class 0 m3.
- The ws client's event handler for focus changes (events 5/6) differs: on
  v2.60F it sends m9 to the object at +0x24 when flag bit 1 of +0x3C is set,
  v2.12F always uses +0x1C.

## Where to look next

1. A debugger on v2.12F. Options: fix MAME's MC driver (below), or a
   browser emulator with a debugger.
2. Compare the frame window class (#18) methods m41–m44 and the app manager
   (#69) m1/m5 between versions: they run around the first redraw and changed
   the most.
3. Compare with a ROM-version-matched app: the v2.12F system disk's TERM.APP
   (14,112 bytes) runs on v2.12F and is a WIMP app with a frame window.

## MAME and v2.12F

MAME's `mc400.cpp` (Nigel Barnes) defaults to BIOS v2.12F for both machines,
but neither boots it; v1.26F boots on `mc400` to the "Psion Graphic User
Interface" screen.

- At reset the ROM reads the power-supply ASIC status (`A3Status`, SIBO
  control 0xCD). MAME always returns `0x02` (PowerFail), commented as needed
  for the MC400/200/Word. v2.12F treats this as error 1: it beeps once
  (routine at C000:E724), then tests a warm-start vector at 0000:0414 and
  jumps into RAM, which is empty, so the CPU runs through blank memory.
- Returning `0x01` (ColdStart) or `0x00` with zeroed RAM gets further but still
  ends up executing empty RAM later in the boot.

## Builds used

The diagnostic builds were the MC200 test build (screen fit, debug log on)
with extra `dlog` calls. The screen-fit code, kept here for when MC200 work
resumes, replaces the fixed window extent in `mcvtwin_w14_m30`:

```c
INT w, h, sw, sh, top, cols, rows;
...
/* fit the screen: the ws client holds its size (640x400 on the MC400,
 * 640x200 on the MC200); the frame adds 10 x 28 around the client */
sw = *(INT *)((UBYTE *)w_ws + 0x78);
sh = *(INT *)((UBYTE *)w_ws + 0x7a);
if (sw < 240 || sw > 2000) sw = 640;
if (sh < 100 || sh > 2000) sh = 400;
top = sh < 250 ? 12 : 20;
cols = (sw - 4 - 10) / vt_cw;
rows = (sh - top - 2 - 4 - 28) / vt_ch;
if (cols > vt_cols) cols = vt_cols;
if (rows > VT_ROWS) rows = VT_ROWS;
vt_resize(cols, rows);
w = vt_cols * vt_cw + 4 + 10;
h = vt_rows * vt_ch + 4 + 28;
ext.tl.x = (sw - w) / 2;
ext.tl.y = top;
```
